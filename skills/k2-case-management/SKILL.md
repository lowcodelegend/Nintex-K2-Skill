# K2 case management

Design reusable, governed, stage-based case solutions. Use `k2-case-management` to determine what components should exist and how they interact. Use `$k2-builder` to implement those components correctly in self-hosted Nintex Automation K2.

## Use and boundary

Use this skill when a request, event, issue, investigation, or exception persists across human and automated activities; collects evidence; moves through controlled stages; has owners, queues, deadlines, or escalations; requires adjudication; and needs a defensible history.

Do not use it for a simple linear approval without a persistent case, single-form CRUD, pure integration, a short-lived workflow without lifecycle state, or a purely technical K2 construction question. `$k2-builder` and its specialists own SmartObjects, SmartForms, Views, workflow generation, rules, methods, controls, integration, deployment, naming, packaging, and technical verification. This skill owns the case architecture and produces design inputs for that implementation.

## Required design workflow

1. Understand the case type, trigger, desired outcome, actors, systems, evidence, constraints, and authoritative sources. Write a substantive plain-language description, positive `useWhen` routing criteria, negative `doNotUseWhen` boundaries, and the expected outcome; do not rely on the case name or field list to convey purpose.
2. Select lifecycle stages from Capture, Validate, Classify and Prioritise, Assign and Route, Investigate or Fulfil, Review and Decide, Resolve and Communicate, and Close and Learn.
3. Start with [the canonical model](assets/case-model.yaml); extend it with solution-specific entities and fields instead of recreating the reusable entities. Define state transitions, guards, commands, and configuration versions. For agent-creatable cases, copy [the creation contract](assets/case-agent-creation-contract.yaml), preserve its required human guidance, declare canonical and namespaced extension fields, increment the immutable contract version when guidance changes, and follow [the agentic framework contract](references/agentic-case-framework.md).
4. Define the parent lifecycle workflow and each child stage workflow using [the standard contract](references/stage-contracts.md).
5. Define data-driven business rules, SLAs, escalations, assignments, queues, human tasks, authority, and evidence requirements.
6. Start the experience from [the canonical case UX](assets/case-ux.yaml), including its required native SmartForms Northstar homepage, extend it instead of rebuilding the shell and standard case components, and follow [the UX contract](references/ux-contract.md). Use [the initiation UX decision and composition contract](references/initiation-ux.md) to choose a compact or guided new-case Form and map its screens in user-task order. For guided Northstar Forms, preserve the governed navigation and command-palette sources, keep the single palette usable after every native screen transition, use short step labels plus question/action screen titles, responsive label-above entry cards, centered completed-step marks, native semantic action-cell alignment, and the original K2 tab strip as the in-shell desktop/mobile stepper; never clone it or permit forward tab clicks to bypass validation. Use native K2 artifacts for navigation, data, actions, rules, and persistence. Use the bounded modern command-palette and dashboard-widget controls only for the interaction and visualization gaps that native controls cannot reproduce at Northstar fidelity. Define optional AI assistance and its human oversight, solution-specific Forms, queues, dashboards, reports, permissions, retention, operations, and recovery.
7. Produce the build manifest described in [implementation checklist](references/implementation-checklist.md), transform it into supported `$k2-builder` and specialist manifests, validate and plan before deployment, then validate the completed solution. Read the selected environment summary first: enable the Langflow command portal only when both `capabilities.langflow.available` and `capabilities.langflow.features.commandPortal` are true, take its base URL, flow ID, and detected component IDs from that profile unless the solution explicitly overrides them, and gate image/document attachment controls independently. Validate every enabled agentic creation contract with `& scripts/case-agent-framework.ps1 validate-contract <contract>` and run `& scripts/case-agent-framework.ps1 selftest`. For remote agent access, copy [the MCP server configuration](assets/case-agent-mcp-server.yaml), follow [the remote MCP contract](references/agentic-case-mcp.md), validate it with `& scripts/case-agent-mcp.ps1 validate-config <config>`, and use `scripts/case-agent-service.ps1` when persistent WinSW hosting is required. Keep production mutations disabled until the case-type runtime is durable and complete. For explicitly requested internal alpha testing only, the development configuration may enable its doubly acknowledged local SQLite creation store; treat those records as development snapshots, not K2 Cases or workflow instances.

Read [architecture](references/architecture.md), [data model](references/data-model.md), [workflow pattern](references/workflow-pattern.md), [business rules](references/business-rules.md), [AI assistance](references/ai-assistance.md), [agentic case framework](references/agentic-case-framework.md), [remote MCP server](references/agentic-case-mcp.md), [UI patterns](references/ui-patterns.md), [UX contract](references/ux-contract.md), [initiation UX](references/initiation-ux.md), and [naming](references/naming-conventions.md). Use [the example](references/example-case-type.md) as an adaptation guide. Copy [case type](assets/case-type-definition.yaml), [stage](assets/stage-definition.yaml), and the [case UX overlay](assets/case-ux-overlay.yaml). Compose the UX overlay with `& scripts/compose-case-ux.ps1 -Overlay <case-ux.yaml> -Output <composed-case-ux.json>`, then run `& scripts/validate-case-model.ps1 -Manifest <case-type.yaml>` and `& scripts/validate-case-ux.ps1 -Manifest <composed-case-ux.json>`. Package and register [the bounded command palette](assets/northstar-command-palette) and [dashboard widget](assets/northstar-dashboard-widget) through `$k2-smartforms-web-components`, prepare the reusable `northstar-native-homepage` Style Profile through `$k2-style-profiles`, then compile mapped UX with `& scripts/compile-case-ux-smartforms.ps1 -Ux <composed.json> -Mapping <mapping.yaml> -BaseManifest <solution-smartforms.json> -Output <combined-smartforms.json>` and deploy it through `$k2-smartforms`. The compiler emits native navigation and KPI Views, bounded palette/widget capture Views, and one modern Form with legacy themes disabled and test Pre-fill explicitly disabled. It automatically chooses a guided initiation for complex composed journeys and emits Form-supported progress text, current-screen validation, Back/Continue, Save, and Review behavior; set `initiation.finalActionMode` to `workflow` for a real Submit seam or `complete` for an explicit saved-draft Finish while workflows are not yet implemented. Use `initiation.stepTabs` for a deliberate persistence-safe screen mapping. It does not emit companion visualization List Views unless an individual dashboard widget, native chart, or report mapping explicitly sets `includeDataAlternative: true`; `tableViewName` optionally names that opt-in View. Every Web Component `listdata` binding is loaded by the owning View's real Init lifecycle and consumes `itemsChangedEventArgs.NewItems`; synthetic control-initializing events are forbidden. The `.yaml` assets use JSON-compatible YAML; the optional Python validators also accept general YAML when PyYAML is installed.

Before native visual iteration, build the reusable multi-page evidence suite with `& scripts/build-case-ux-visual-evidence.ps1 -Manifest <composed.json> -OutputDirectory <ux-evidence>`. It renders dashboard, My Work, initiation, workspace, and reports plus empty, validation-error, SLA-breached, read-only, and long-content states; captures every declared viewport through Edge device emulation; and rejects browser-measured horizontal overflow. These HTML files are design references only. Implement accepted patterns through `$k2-smartforms`, then compare authenticated Runtime captures with the retained evidence.

After deployment, capture the native result with `& scripts/capture-k2-runtime-ux-evidence.ps1 -RuntimeBaseUrl <base-url> -FormNames <forms> -OutputDirectory <runtime-evidence> -TrustedAuthHost <host>`. It uses Integrated Windows authentication, captures the canonical desktop/laptop/tablet/mobile dimensions by stable Form name, and fails on authentication/title mismatch, insufficient rendered content, horizontal document overflow, or unexpected browser diagnostics. For guided Forms, pass ordered real actions through `-InteractionClickNames` and a governed search term through `-CommandPaletteProbeTexts`; this also gates completed-tick geometry and palette operation after navigation. Retain its JSON report and images as the authoritative visual gate; record any allowlisted platform diagnostic or control-level responsive limitation as explicit errata.

## Non-negotiable principles

- The Case SmartObject is the lifecycle system of record; workflow instance status is not case state.
- The parent workflow alone owns lifecycle orchestration and authoritative transitions. Child workflows execute one stage, persist a standard result, and never start an unrelated stage.
- Every stage has explicit entry and exit criteria; every transition is guarded, version-aware, and logged. Re-entry creates a new stage instance.
- Material decisions remain attributable to a human. AI is optional and advisory unless an explicitly approved policy says otherwise; it never writes authoritative state directly.
- Let a reusable agent discover immutable case-type creation and context contracts. Require each case type to explain its purpose, positive and negative routing criteria, and expected outcome so an agent never selects from a label alone. Reject undeclared fields, arbitrary extensions, caller-supplied identities, dynamic SQL, and unregistered adapters. Bind drafts, file handles, previews, and idempotency to the authenticated principal. Creating a draft Case never implies lifecycle submission.
- Expose production remote agent tools only through authenticated HTTPS Streamable HTTP with strict Host/Origin and network allowlists. Keep static bearer mode limited to controlled internal bootstrap use, issue one scoped/expiring token per client, and require durable providers plus exact adapters before enabling production `create_case`. The explicit unauthenticated alpha mode may persist synthetic development snapshots locally only when both mutation acknowledgements are present; it never represents K2 or workflow creation.
- Use one declared time basis (normally UTC) and append-only history. Keep reference data, rules, routing, SLAs, and transition paths data-driven where practical.
- Put long waits in workflows, not UI rules. Respect external systems as authoritative for their domains. Design integrations for idempotency, correlation, timeout, and bounded retry.
- Keep the reusable lifecycle framework free of case-type-specific branches. Record the active configuration and workflow versions on runtime records.
- Keep the reusable case shell, dashboards, initiation mechanics, workspace header/lifecycle/actions, queues, visual states, and accessibility contract free of case-type-specific branches. Extend stable templates rather than recreating them.
- Treat the native SmartForms Northstar homepage as the default role landing for case operations. Always set `useLegacyTheme: false`, including when no explicit Style Profile is selected, so K2 uses its plain modern default. Generated Northstar Forms explicitly set `useStyleProfile` to match the mapped profile and set `useCommonHeader: false` plus `useCommonFooter: false`; the Northstar shell is the Form's presentation contract and must not inherit redundant environment framework Views. The full-page `northstar-case-homepage` control is a temporary visual oracle only and must not be generated into new solutions. Use `northstar-command-palette` and the bounded `northstar-dashboard-widget` variants only where native controls cannot match the accepted interaction or visual contract; never substitute a legacy DLL custom control.
- Declare `homepage.commandPalette.viewTitle` as the shared case-compiler/Style-Profile contract and use `Command palette` for the canonical Northstar profile. Preserve it when replacing the palette with an `agenticChat` clone. Prefer `agenticChat.integration: command-portal` for the large Langflow client with a session sidebar, new/switch/clear/delete, streamed responses, Stop, and capability-gated file attachments; retain the embedded-widget mode only for compatibility. Require `agenticChat.authentication.mode` to be `server-open-alpha` or `server-proxy`; never place a reusable Langflow key, token, header, arbitrary tweak, or secret reference in browser-visible artifacts. Open alpha may call an unauthenticated HTTPS Langflow, or an HTTP loopback instance, and its flow-owned case MCP during internal development; chat files are not case evidence. Verify the real K2 palette with CDP pointer input and Ctrl/Cmd+K plus portal session, history, stream, upload, clear/delete, fixed-overlay layout stability, focus return, K2 modal precedence, desktop/mobile behavior, and accessible failure handling.
- Do not claim native YAML import, DMN, child-output behavior, or K2 types/methods that `$k2-builder` does not confirm. The YAML assets are design inputs, not deployable K2 artifacts.
