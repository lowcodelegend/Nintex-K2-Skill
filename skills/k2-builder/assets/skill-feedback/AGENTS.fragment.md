## K2 skill feedback loop

- Read `docs/skill-learnings.md` before substantial project work and preserve its stable learning IDs and history.
- Add or update a learning whenever project work reveals behavior, friction, a missing guardrail, or a reusable technique that could improve an affected K2 skill. Record evidence without credentials, tokens, personal data, or other secrets.
- Treat installed/shared skills as read-only during ordinary project work. The learning log is the handoff queue for skill owners unless the user explicitly asks to change the skill repository.
- Review open learnings at each release, milestone handoff, or before closing substantial work, and at least every 14 days while the project is active. Update `Last reviewed` and append a feedback-history entry.
- During each review, suggest up to three highest-value actions: a local project improvement in a focused commit, an upstream code pull request, or an upstream documentation-only pull request. State the affected skill, evidence, acceptance criteria, and recommended destination.
- Do not silently commit unrelated improvements, push branches, or open pull requests. Implement, commit, push, or submit only when the current user request or repository workflow authorizes it; otherwise leave a ready-to-action suggestion or patch plan in the learning log.
