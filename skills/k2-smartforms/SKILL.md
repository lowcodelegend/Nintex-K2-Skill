# K2 SmartForms builder

Build checked-in Forms/Views through supported K2 APIs; never edit K2 databases or automate Designer UI.

## Workflow

1. Confirm self-hosted K2 Five and existing SmartObjects. If `$k2-builder` is installed, validate its selected environment profile before discovery. Resolve only the Style Profile/header/footer dependencies explicitly selected by the application or opted into by a Form; an unused environment framework may remain `unselected` and must not block plain modern Forms. When a requested custom Style Profile does not exist, create and verify it first with `$k2-style-profiles`.
2. Read [design.md](references/design.md) and [manifest.md](references/manifest.md). Create a stable, version-free manifest under one application root.
3. Select fields, methods, sections, two-column label-above responsive layout, required state, literal Create defaults, lookups, help content, titles, tabs, and Form composition for each user/process stage. Every capture View must include each selected method's required properties except a master-detail foreign key supplied by the Form. Keep user inputs visible/editable and declare them in `requiredProperties`; keep system-managed values off the layout and supply them with `defaultValues`.
4. Run `scripts/k2forms.ps1 doctor --manifest <path>`, then `plan` and review categories, collisions, replacement, dependencies, framework, and verification scope.
5. Deploy with `deploy --manifest <path> --confirm`; it verifies in the same run. After native workflow integration or a profile/header/footer selection change, run `reconcile --manifest <path> --confirm` to restore manifest-declared child loads and remove redundant framework bindings/instances in place, then verify the workflow integration again. Use separate `verify`/`inspect` only for drift diagnosis or evidence, and `view-definition --view <exact-name>` for read-only source/layout diagnosis through the supported management API. For an explicitly diagnosed generator defect on an existing View, prove the update against a disposable View before using guarded `repair-view --view <exact-name> --expected-id <guid> --backup <new-path> --confirm`; it preserves identity/dependencies and refuses drift.
6. Browser-test authenticated Create, Read/list-click, Update, Delete, lookup loading, responsive behavior, and any Worklist/task flow. Report GUIDs, versions, categories, Style Profile/theme mode, rule checks, URLs, and skipped tests.

After interruption use `--resume`, which preserves existing declared artifacts and creates missing ones. Use `--forms-only` to regenerate Forms over known-good Views. For a reviewed, same-owner Form draft use `checkin --form <exact-name> --confirm`; never publish another designer's work.

## Design gates

The linked design/manifest references are authoritative. Key constraints are:

- Prefix complete-solution Forms, Views, category leaf, and generated SmartObject references with `<CODE>.`; preserve K2-sanitized SmartObject system names exactly. Ordinary artifacts go under `Views`/`Forms`; managed lookup and matrix UX goes under `Admin\Views`/`Admin\Forms`.
- Bind every user-selectable controlled code or foreign key to a declared SmartObject lookup source. Declare it in `lookupRequiredProperties` so validation rejects an unbound dropdown contract. Retain SQL-derived length/format constraints in `validations`; for a governed dropdown the CLI validates the complete bounded lookup value domain against them instead of applying inapplicable TextBox `MaxLength` or Validation Pattern properties. It rejects more than 10,000 lookup values when it cannot prove the bounded domain. The CLI generates and verifies one control-scoped SmartObject association source plus exactly one View-initialization List action for each dropdown; missing either declaration produces unresolved Designer rules and an empty list. Give every business-managed lookup Admin capture/list UX; omit it deliberately for external/system vocabularies.
- Treat every editable property ending in `CountryCode` or `CountryId` as a governed lookup even when the requirement merely calls it a short string. The manifest must include both `lookupControls` and `lookupRequiredProperties`; reuse an enterprise Country SmartObject or the bundled `$k2-sql-smartobjects` ISO catalog, and never present country codes as free text.
- Mirror every user-editable database invariant in `view.validations`: nullability/required input, SQL text length, minimum length, numeric bounds, format/regex checks, and bit checks that require `true`. Never rely on a SQL exception or broker truncation as form validation. The CLI applies native `MaxLength`, solution-owned K2 Validation Patterns, and validation-group conditions before Create/Update; `mustBeTrue` is required for consent checkboxes because K2 `IsRequired` alone accepts `false`. When a SQL manifest is present, copy its `formConstraints` contract exactly and retain `sourceConstraint` for named checks.
- For master-detail, use a capture master plus every required editable `capture-list` child and declare them under `form.masterDetail.details`. One Form Save handles master Create/Update, returned-key transfer, and each child's `Added`/`Changed`/`Removed` states. Keep SmartObject method actions inside rules owned by their Views: the Form button may contain only synchronous View-event calls, explicit transfers from the master key to declared View parameters, validation, navigation, and feedback. Generate dedicated `SourceType="Rule"` master Create and Update seams; never make the Form call the generated master Create/Update button events, because those control-event references can leave the Form Rule Designer spinning. Compose the button's persistence paths as one local blank-key `IfLogicalHandler` immediately followed by a native `Type="Else"` / `ElseLogicalHandler` with no second condition. Never emit sibling blank/not-blank conditions: Create populates the key, and K2 can re-evaluate the later condition after a modal action resumes, causing Update in the same click. The View-owned Create seam must synchronously run Create and then Read the new row before the Form transfers the key or saves children; this hydrates hidden/defaulted persisted fields for a later intentional Update. Every generated custom View rule must retain the Event's View-name location but set each Handler `Location` to canonical lowercase `view`; a View-name Handler location is accepted by K2 storage and its analyzer but leaves the browser Rule Designer spinning. Every synthetic Form Button must have K2's canonical `Type="System"` control-event declaration immediately before its user `OnClick` rule; K2 stores and analyzes a user rule without that declaration, but the browser cannot hydrate its rule editor. The local blank-key condition must use `Name="AdvancedCondition"`, `Location="Form"`, and no Condition-level `InstanceID`; the source Item owns `SourceInstanceID`. The server accepts invented `SimpleBlankViewFieldCondition` names and local InstanceIDs, but the browser has no condition editor for that shape. The detail View's Save event owns item-state persistence; generated filtered Load and review Read rules own their method calls. Never clone a View method action directly into a local Form button rule or create a partial inheritance tree; either shape can leave the Designer rule editor spinning. Optional `masterDetail.review` loads a read-only review View from the saved key and focuses its tab only after persistence. Treat every `List` action with `ControlID` as dropdown population, preserve it unchanged, and never classify, remove, or clone it as a detail data load. Replace only unfiltered, control-free detail Lists with the parameterized View-owned Load seam, and invoke it after every nonblank master-key Read path. Never flatten or remove a child collection to recover from generation or integration failure.
- Regenerate the Form when upgrading a pre-0.35 master-detail application. Identity-repair its manifest-owned Views too when upgrading from pre-0.33; `reconcile` can restore Form load handlers only after all custom persistence/load seams already exist.
- For guided initiation, use 3–7 task-oriented tabs and declare `guidedJourney` with exactly one final-action contract. Keep the stepper `label` short and use optional `title` for the content-card question/action. Use `workflowStartButton` plus final `advance: "submit"` only when a real start workflow is ready. During iterative delivery with no workflow, use `completionButton` plus final `advance: "complete"`; it adds a native Finish action whose popup must truthfully say the draft is saved and not submitted. Switching modes is declarative. The CLI adds the journey title/description, one native read-only Progress control per screen, a screen title and purpose statement, non-destructive Back, and Continue that runs the Form validation group before a native Focus action. The penultimate `advance: "save"` screen must contain the final master-detail child and relies on the existing `btnSave` persistence/review seam. Action alignment is semantic and generator-owned: Back/Previous and test Pre-fill receive native left-aligned K2 Table cells; Continue, Save, Finish, and Submit receive native right-aligned cells. No manifest alignment declaration is needed. Style Profiles may add spacing and responsive polish but must not be the only alignment mechanism. Never attach workflow Start to Save Draft, emit both final actions, or leave an inert Submit button. Do not invent decorative tabs or split one persisted View without a valid data-ownership seam.
- Use named list/details/My Tasks tabs for workflow shells, `listClickTabNavigation` for drill-in, and the native Worklist control when users act in the application. Keep compact Admin Forms stacked unless tabs help.
- Use responsive two-column Item Views by default: each 50% cell stacks a bold colon-suffixed Label above its control. Keep section boundaries from sharing a row and make narrative/File controls span both columns. Use `labels-left` with `layoutColumns: 4` only as an explicit dense-desktop exception. Group related fields with `sections`; each section compiles to a native K2 Table row and Label header, and field order must remain task-oriented. Email properties and `singleLineProperties` compile to TextBox controls even when SQL inference returns Memo. Use `help` for consent, legal, policy, or unfamiliar choices that cannot be accepted responsibly without explanatory content.
- Put transient rule values in hidden `tblDebug` Data Labels. Use `hiddenProperties` only to retain bound technical/defaulted fields without presenting them in a dedicated task View. `defaultValues` also rewrites the Create rule input to a literal, so system values do not depend on a hidden control or SQL default. Hidden control method mappings are rewritten to the retained ViewField identity before layout removal so K2 cannot persist an orphan Control reference. Capture Views remove the property's dedicated row; `capture-list` Views remove the matching Header/Display/Footer/Edit column only and must retain all four structurally aligned template rows. Generated `capture-list` Views disable K2's `Enable Add new row link` setting by omitting `ShowAddRow`; K2 treats the property's presence as enabled regardless of a stored false value. Use the native Add toolbar action for explicit row staging. Give every Form view instance a user-facing title or a documented `untitledViews` exception.
- Always generate Forms with `useLegacyTheme=false`, whether a custom Style Profile is selected or deliberately omitted. Without a Style Profile, disabling legacy themes enables K2's plain modern default theme. Never set `useLegacyTheme=true`; `theme` is required legacy generator metadata only.
- Every newly generated Form includes one test-only `Pre-fill` button. On a guided multi-step Form it must be at the bottom of the first physical screen; on other Forms it remains at the bottom of the last visible panel. Its containing native K2 Table cell is implicitly left-aligned. It fills editable controls with constraint-aware dummy values, uses the first available declared lookup value, and reports fields that still require manual input such as File uploads, empty/cascading lookups, impossible format/length combinations, and custom patterns without a valid `validations[].example`. Generated values must fit before transfer; never clip a descriptive placeholder to satisfy `maxLength`. Treat the CLI's `ERRATA test-only Pre-fill` line as an open go-live blocker and copy it into the solution errata register. Before production, set `form.preFill.enabled=false` with a non-empty `disabledReason`, regenerate the Form, verify the helper is absent, and resolve the erratum. Never expose the helper on a live production Form.
- Use manifest-declared `charts` on dedicated capture Views backed by parameterless List methods. Do not add companion List Views by default: the chart's capture View already owns and loads the governed projection. Add a separate list View only when the customer explicitly requires a sortable/exportable or accessible data alternative; provide a meaningful empty state on every generated visual and optional companion.
- Use manifest-declared `metricCards` on a dedicated capture View for governed one-row operational summaries and `lifecycleTrackers` on a capture View's read-only current-stage property. These transformers preserve native SmartObject bindings while replacing generated source rows with responsive presentation controls.
- Use `view.webComponents` only to place one already registered modern K2 5.9+ Web Component as the sole visible body of a bounded capture View. `$k2-smartforms-web-components` owns authoring, validation, packaging, and registration; this skill owns View/Form placement, optional server-user-scoped SmartObject List binding from the owning View's real Init lifecycle, View-owned event actions, Designer hydration, runtime verification, and dependency-safe cleanup. Never generate a synthetic control `Initializing` rule for list data. Never use this seam for a case-management full-page shell, legacy DLL controls, or arbitrary HTML injection.
- Treat Style Profiles and common header/footer Views as explicit Form dependencies, never sticky environment decoration. `application.styleProfile` and an enabled `application.commonHeader` default onto the application's Forms, while `form.useStyleProfile`, `form.useCommonHeader`, and `form.useCommonFooter` override that selection per Form. An omitted `application.commonHeader` means no framework unless a Form explicitly opts into the selected environment contract. Generation omits unused dependencies; `reconcile` removes the known redundant StyleProfile property, header/footer layout instances, controls, and lifecycle actions without deleting the external framework artifacts. Preserve exact instance settings, first/last placement, initialization bindings, server-load rule calls, combined control transfer, and discovered order only where selected. PSF names/mappings are optional discovered conventions, never defaults.
- Master-detail Save validates all `requiredProperties` and `validations` through a native K2 Form validation group immediately before calling the generated master Create/Update seam. The internal `K2Skills.MasterDetail.Create.*` and `Update.*` View rules are callable persistence seams, not independent user-triggered validation paths; their owning Form call must carry validation. Ordinary View Create/Update/Save/Submit actions still run the View validation group immediately before persistence; use `validationMethods` for differently named mutating methods. Verify native max lengths, validation-pattern GUID/message, numeric conditions, and must-be-true conditions in the stored definition. A configured review tab is hidden initially by default and is revealed only after validation, persistence, and review Read complete. Generated UX is still a baseline: validate accessibility, required-state messaging, empty/long values, destructive confirmation, and business rules in Designer/browser.

## Cleanup and safety

- Keep `replaceExisting=false` unless replacement of exact names is authorized. Replacement deletes declared Forms before Views and produces new GUIDs; it does not preserve manual edits.
- Ordinary replacement/cleanup blocks managed Views used by undeclared Forms.
- Treat cleanup as destructive. For a builder-validated solution use `cleanup --manifest-only`: it skips broad discovery but still requires exact names and either the expected category or a strict-ancestor orphan category. It discards a current-identity checkout before deletion and refuses a foreign checkout.
- Use unique disposable names in development; never add release numbers to artifact names.
- Keep runtime artifacts checked in unless a draft is intentional.

## Boundary

The CLI supports capture, list, content, and editable-list Views; responsive two-column label-above layout by default and explicit dense label-left/four-column layouts, native section headers, single-line semantic inputs, More info buttons with help popups, required/length/range/format/must-be-true validation, literal Create defaults, hidden-until-saved review tabs; native GenericChart, metric-card, lifecycle Progress, and guided-journey Progress/navigation composition; sole-body placement of one registered modern Web Component; composed/titled/tabbed Forms; test-only constraint-aware Pre-fill helpers with a governed production opt-out; lookups/cascades/Admin UX; Worklist tabs and list navigation; modern Style Profiles and external frameworks; master-detail persistence/load rules; hidden variables; resumable/forms-only deployment; verification; and manifest-owned cleanup.

It does not support generic Form-level Save synthesis for ordinary non-master-detail CRUD, arbitrary conditional visibility/rules, control authoring/registration, legacy custom controls, mixed native/custom body composition, multi-column lookup templates, preservation of Designer customizations during replacement, export rollback packages, or authenticated browser automation. Retain generated View buttons for ordinary CRUD and report unsupported behavior as errata.

Read [cli.md](references/cli.md) for exact commands and exit codes. Treat the installed package and its references/help/output as the capability contract. During ordinary work do not inspect source, decompile, or infer unsupported behavior. Only an explicit repair request authorizes development-repository changes; never edit an installed skill in place.
